# Дизайн: фронтенд KanbanBoard + доработки бека

Дата: 2026-08-30. Статус: на ревью.

## 1. Цель и контекст

Сделать веб-фронтенд для существующего бека KanbanBoard (ASP.NET Core MVC, .NET 9, PostgreSQL, cookie-auth). Фронт живёт в `wwwroot` и отдаётся этим же приложением (same-origin, CORS не нужен). Референс по UX — Jira / Яндекс.Трекер. Попутно дорабатываем бек: добавляем недостающие эндпоинты и чиним найденные баги (решение: всё делаем сами, другу задачи не откладываем).

Роли: фронт-код пишет Claude целиком; решения принимает Павел.

## 2. Утверждённые UX-решения

- **Компоновка** — «Jira/Я.Трекер»: постоянный левый сайдбар (список досок, внизу — переключатель темы и выход), контент справа.
- **Темы — две, с переключателем**: светлая «строгая» (белый фон, серо-синяя палитра, синий акцент, малые скругления) и тёмная «Linear» (графит, индиго-акцент, тонкие рамки вместо теней). Все цвета — через CSS-переменные; выбор в `localStorage`, по умолчанию — системная тема.
- **Панель задачи** — широкая (~55–60% экрана), поверх доски, две колонки: слева заголовок, описание, комментарии; справа свойства (статус, исполнитель, дедлайн, автор, дата создания, вложения, история статусов).
- **Главная** — сетка карточек досок (имя, описание, автор, дата, кнопка «+ Новая доска», пустое состояние «создай первую доску»).
- **Логин** — центрированная карточка, переключатель «Вход / Регистрация», ошибки под формой («Неверный логин или пароль» / «Логин уже занят»).

## 3. Стек и архитектура фронта

**Vue 3 без сборки**: ES-модули, без node/npm/бандлера. Vue вендорим в репозиторий (`wwwroot/lib/vue.esm-browser.prod.js`, зафиксированная версия 3.5.x) — работает офлайн, запуск фронта = F5 в Rider, ничего кроме .NET не нужно.

```
wwwroot/
  index.html                 — точка входа SPA
  lib/vue.esm-browser.prod.js
  css/
    tokens.css               — дизайн-токены обеих тем ([data-theme])
    app.css                  — общие стили
  js/
    app.js                   — createApp, hash-роутер (свой, ~50 строк)
    api.js                   — единственное место общения с беком (fetch-обёртка)
    store.js                 — reactive-состояние: юзер, доски, текущая доска
    components/
      LoginPage.js  Sidebar.js  BoardsGrid.js
      BoardView.js  TaskColumn.js  TaskCard.js
      TaskPanel.js  CommentList.js  BoardSettingsModal.js
      ThemeToggle.js  Toast.js
```

Ключевые правила:

- **Роутинг** — hash-роуты (`#/login`, `#/`, `#/boards/5`, `#/boards/5/tasks/42`). Серверу ничего настраивать не надо: `HomeController.Index` отдаёт одну страницу, F5 работает на любом роуте. Компоненты — обычные `.js` с шаблонами-строками.
- **`api.js` — карантин особенностей бека**: тела ошибок бек отдаёт плоскими строками — читаем как текст; клиентская дублирующая валидация длин для мгновенного UX (имя задачи ≤ 50, имя доски ≤ 200, описания ≤ 3000, коммент ≤ 10000, логин ≤ 100).
- **Razor не трогаем**: `Views/Home/Index.cshtml` остаётся тонкой обёрткой, вся жизнь — в `wwwroot`.

## 4. Экраны и роуты

| Роут | Экран |
|---|---|
| `#/login` | Вход/регистрация |
| `#/` | Сетка досок |
| `#/boards/{id}` | Доска: шапка (имя, поиск по карточкам, аватарки участников, кнопка настроек) + колонки с карточками |
| `#/boards/{id}/tasks/{taskId}` | Та же доска + панель задачи поверх |

Карточка задачи на доске: название, бейдж дедлайна (подсветка просроченного), аватар исполнителя (или «без исполнителя»), счётчики 💬 и 📎.

Настройки доски — модалка с вкладками: **Участники** (список, добавить по логину с поиском-автокомплитом, удалить), **Колонки** (создать, переименовать, удалить пустую, перетащить порядок), **О доске** (переименовать, описание, удалить доску с подтверждением).

Drag&drop карточек — нативный HTML5 DnD: между колонками и внутри колонки (после появления поля Order).

## 5. Потоки данных

- **Старт приложения**: `GET /api/auth/me` → 401 → `#/login`; иначе `GET /api/boards` → сайдбар + сетка.
- **Открытие доски**: параллельно `GET board`, `GET statuses`, `GET tasks`, `GET users`. Задачи группируются по `StatusId`, сортируются по `Order`.
- **Deep-link на задачу**: если доска уже загружена — берём задачу из стора; при прямом заходе/F5 — `GET .../tasks/{taskId}` (новый эндпоинт), панель открывается не дожидаясь полной загрузки доски.
- **Панель задачи**: параллельно комментарии (вложения придут внутри них), вложения задачи, история.
- **DnD и отправка комментов — оптимистичные**: UI меняется сразу, запрос уходит следом, при ошибке — откат и тост.
- **Поиск по доске** — клиентский фильтр по уже загруженным задачам (серверный `?search=` не используем).
- **Живых обновлений нет** (websocket/поллинг): осознанное ограничение v1 — правки второго участника видны после обновления страницы.

## 6. Доработки бека

### 6.1 Новые эндпоинты

| Метод и путь | Что делает |
|---|---|
| `GET /api/boards/{boardId}/tasks/{taskId}` | Одна задача → `TaskResponse`. 404 — нет задачи/не участник. |
| `GET /api/boards/{boardId}/tasks/{taskId}/history` | История статусов → `List<StatusHistoryResponse>` (от новых к старым). |
| `POST /api/boards/{boardId}/statuses` | Создать колонку. Тело `StatusRequest { Name }`. `Order` = max+1. |
| `PUT /api/boards/{boardId}/statuses/{statusId}` | Переименовать колонку. Тело `StatusRequest { Name }`. |
| `DELETE /api/boards/{boardId}/statuses/{statusId}` | Удалить **пустую** колонку; если в ней есть задачи — 409. Последнюю колонку доски удалить нельзя — 409. |
| `PATCH /api/boards/{boardId}/statuses/{statusId}/position` | Тело `{ Position }` — переставить колонку, сервер переиндексирует. |
| `PATCH /api/boards/{boardId}/tasks/{taskId}/position` | Тело `{ StatusId, Position }` — перенос между колонками и/или перестановка. При смене статуса пишет строку истории. Сервер переиндексирует затронутые колонки. |

Существующий `PATCH .../tasks/{taskId}/status` не трогаем (обратная совместимость с тем, что тестировал друг); фронт для DnD использует только `/position`.

### 6.2 Миграция

Одна миграция `AddOrdering`:
- `Status.Order int` — бекфилл по текущему `StatusId`;
- `Task.Order int` — бекфилл по `CreationDate` внутри своей колонки.

### 6.3 Багфиксы и поведение

- **`TaskService.CreateTaskAsync` читает `WorkerId`** из запроса (сейчас исполнитель всегда = автор). Валидирует, что исполнитель — участник этой доски.
- **Исполнитель опционален**: `TaskRequest.WorkerId → int?`, `TaskResponse.Worker → UserResponse?`, цепочка сервиса пропускает null.
- **Создание задачи пишет первую строку истории** (начальный статус, автор = создатель).
- **Права:** редактировать задачу (`PUT`) может любой активный участник доски (сейчас — только автор). Удаление без изменений (автор задачи или владелец доски).
- **Auth:** неверные логин/пароль → `401` c текстом «Неверный логин или пароль» (сейчас 409 «Такой логин отсутствует»); 409 остаётся только у регистрации («Логин уже занят»); `GET /api/auth/me` и `POST /api/auth/logout` получают `[Authorize]` → анонимный `/me` = 401 (сейчас 400).
- **Валидация:** `[ApiController]` на все 7 API-контроллеров; на request-DTO — `[Required]`/`[MaxLength]` зеркалом сущностей (TaskName 50, Board Name 200, описания 3000, коммент 10000, логин 100) + `[MinLength(6)]` на пароль регистрации. Кривой ввод → 400 (сейчас 500).

### 6.4 Доработки DTO

- `StatusResponse`: + `Order`.
- `TaskResponse`: + `BoardId`, + `Order`, `Worker` → nullable, + `CommentsCount`, + `AttachmentsCount`.
- `CommentResponse`: + `TaskId`, + `Attachments: List<AttachmentResponse>` (убирает N+1).
- `StatusHistoryResponse`: + `StatusChangeId`, + `Author: UserResponse`.

Стиль — как в существующем коде друга: те же паттерны сервисов (null → 404), `[Authorize]`, `CancellationToken`, плоские строки в телах ошибок.

## 7. Обработка ошибок (фронт)

- `401` на любом запросе (кроме логина) → чистим стор → `#/login`.
- `404` доски → экран «Доска недоступна» (бек не различает «удалена» и «вас исключили» — фронт и не пытается).
- `400` (валидация) → сообщение под полем формы; `409` → предметное сообщение («колонка не пуста», «логин занят»).
- Сетевые ошибки / 5xx → тост «Что-то пошло не так», детали в консоль.
- Оптимистичные операции (DnD, комменты) при ошибке откатываются + тост.
- Пустые состояния: нет досок / пустая колонка / нет комментариев — осмысленный текст.

## 8. Не входит в v1

- Живые обновления (websocket/поллинг).
- «Мои задачи» кросс-бордно (в сайдбаре зарезервировано место).
- Редактирование профиля (смена пароля/логина, аватары) — на беке нет, не добавляем.
- Мобильная вёрстка: цель — десктоп; на планшете должно быть терпимо, специально не вылизываем.

## 9. Проверка

- Каждый новый/изменённый бек-эндпоинт — ручной прогон через Swagger (успех + 401/404/400/409).
- Фронт — сквозные сценарии в браузере: регистрация → создание доски → колонки → задачи (с исполнителем и без) → DnD между/внутри колонок → комменты с вложениями → история → настройки → удаление → обе темы.
- Финальная приёмка: Павел открывает `http://localhost:5110` и смотрит глазами.
