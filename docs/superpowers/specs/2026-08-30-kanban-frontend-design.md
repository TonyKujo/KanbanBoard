# Дизайн: фронтенд KanbanBoard + доработки бека

Дата: 2026-08-30. Статус: на ревью (после само-проверки фактчеком по коду).

## 1. Цель и контекст

Сделать веб-фронтенд для существующего бека KanbanBoard (ASP.NET Core MVC, .NET 9, PostgreSQL, cookie-auth). Фронт живёт в `wwwroot` и отдаётся этим же приложением (same-origin, CORS не нужен). Референс по UX — Jira / Яндекс.Трекер. Попутно дорабатываем бек: добавляем недостающие эндпоинты и чиним найденные баги (решение: всё делаем сами, другу задачи не откладываем).

Роли: фронт-код пишет Claude целиком; решения принимает Павел. Язык интерфейса — русский.

## 2. Утверждённые UX-решения

- **Компоновка** — «Jira/Я.Трекер»: постоянный левый сайдбар (список досок, внизу — переключатель темы и выход), контент справа.
- **Темы — две, с переключателем**: светлая «строгая» (белый фон, серо-синяя палитра, синий акцент, малые скругления) и тёмная «Linear» (графит, индиго-акцент, тонкие рамки вместо теней). Механика — см. §3.
- **Панель задачи** — широкая (~55–60% экрана), поверх доски, две колонки: слева заголовок, описание, комментарии; справа свойства (статус, исполнитель, дедлайн, автор, дата создания, вложения, история статусов — свежие сверху, без пагинации).
- **Главная** — сетка карточек досок (имя, описание, автор, дата, кнопка «+ Новая доска», пустое состояние «создай первую доску»).
- **Логин** — центрированная карточка, переключатель «Вход / Регистрация», ошибки под формой («Неверный логин или пароль» / «Логин уже занят»).
- **Аватары** — картинок на беке нет и не будет: кружок с первой буквой логина, цвет — детерминированный хеш от логина.

## 3. Стек и архитектура фронта

**Vue 3 без сборки**: ES-модули, без node/npm/бандлера. Vue вендорим в репозиторий: `wwwroot/lib/vue.esm-browser.prod.js`, версия **3.5.13** (пиним точно). Запуск = обычный запуск .NET-приложения.

```
Views/Home/Index.cshtml      — SPA-оболочка: <div id="app">, <link>, <script type="module">
wwwroot/
  lib/vue.esm-browser.prod.js
  css/
    tokens.css               — дизайн-токены обеих тем
    app.css                  — общие стили
  js/
    app.js                   — createApp, hash-роутер (свой, без библиотек)
    api.js                   — единственное место общения с беком (fetch-обёртка)
    store.js                 — reactive-состояние: юзер, доски, текущая доска
    strings.js               — все строки UI (русский): ошибки, пустые состояния, подписи
    components/
      LoginPage.js  Sidebar.js  BoardsGrid.js
      BoardView.js  TaskColumn.js  TaskCard.js
      TaskPanel.js  CommentList.js  BoardSettingsModal.js
      ThemeToggle.js  Toast.js
```

Ключевые правила:

- **Точка входа одна** — Razor `Views/Home/Index.cshtml` (отдаётся `HomeController.Index` на `/`). Файла `wwwroot/index.html` нет. `Index.cshtml` и `_Layout.cshtml` редактируются: становятся тонкой обёрткой с подключением css/js и `<div id="app">`.
- **Роутинг** — hash-роуты (`#/login`, `#/`, `#/boards/5`, `#/boards/5/tasks/42`). Фрагмент не уходит на сервер, F5 на любом роуте = `GET /` — серверу ничего настраивать не надо.
- **`api.js` — карантин особенностей бека**:
  - тела ошибок двух видов: валидационный 400 от `[ApiController]` — JSON `ValidationProblemDetails` (`errors[поле][]`), всё остальное — плоские строки; api.js нормализует оба вида в `{ status, message, fieldErrors }`;
  - даты (дедлайн) отправляем строго UTC ISO-8601 с `Z` — `<input type="datetime-local">` даёт `Unspecified`, Npgsql на таком кидает 500;
  - клиентская дублирующая валидация для мгновенного UX: имя задачи ≤ 50, имя доски ≤ 200, имя колонки ≤ 100, описания ≤ 3000, коммент ≤ 10000, логин ≤ 100, пароль ≥ 6.
- **Темы**: три состояния — light / dark / system. Токены светлой — на `:root`, тёмной — в `:root[data-theme="dark"]` и в `@media (prefers-color-scheme: dark)` для system-режима (атрибут при system не ставится). Выбор — в `localStorage` (`kb.theme`); инлайн-скрипт в `<head>` выставляет атрибут до загрузки модулей, чтобы тема не мигала.
- **Дев-цикл**: в `Program.cs` добавляем `app.UseStaticFiles()` — иначе `MapStaticAssets` отдаёт файлы по вшитым на этапе сборки ETag/длинам, и правка js/css без пересборки приезжает битой.

## 4. Экраны и роуты

| Роут | Экран |
|---|---|
| `#/login` | Вход/регистрация |
| `#/` | Сетка досок |
| `#/boards/{id}` | Доска: шапка (имя, поиск по карточкам, аватарки участников, кнопка настроек) + колонки с карточками |
| `#/boards/{id}/tasks/{taskId}` | Та же доска + панель задачи поверх |

Карточка задачи на доске: название, бейдж дедлайна (подсветка просроченного), аватар исполнителя (или «без исполнителя»), счётчики 💬 и 📎 (вложения самой задачи, без комментариев).

Настройки доски — модалка с вкладками: **Участники** (список; добавить по логину через автокомплит на существующем `GET /api/users/search`; удалить), **Колонки** (создать, переименовать, удалить пустую, перетащить порядок), **О доске** (переименовать, описание, удалить доску с подтверждением). На беке всё это разрешено только владельцу доски — фронт скрывает недоступные контролы, сравнивая `board.Author.UserId` с `/me`; участникам вкладки видны read-only. Ошибки настроек показываются внутри модалки и не роняют экран доски.

Drag&drop карточек — нативный HTML5 DnD: между колонками и внутри колонки. Перетаскивание порядка колонок — в модалке настроек.

## 5. Потоки данных

- **Старт приложения**: `GET /api/auth/me` → 401 → `#/login`; иначе `GET /api/boards` → сайдбар + сетка.
- **Открытие доски**: параллельно `GET board`, `GET statuses`, `GET tasks`, `GET users` (участники доски). Колонки и задачи приходят уже отсортированными по `(Order, Id)`; задачи группируются по `StatusId`.
- **Deep-link на задачу**: если доска уже загружена — задача из стора; при прямом заходе/F5 — новый `GET .../tasks/{taskId}`, панель открывается не дожидаясь полной загрузки доски. 404 задачи → тост «Задача не найдена» + редирект на `#/boards/{id}`.
- **Панель задачи**: параллельно комментарии (вложения внутри них), вложения задачи, история.
- **DnD — оптимистичный**: карточка переезжает сразу, `PATCH /position` следом; ответ сервера (список затронутых `{Id, StatusId, Order}`) применяется поверх; при ошибке — откат + тост. На одну карточку — один in-flight запрос: пока PATCH в полёте, карточка не перетаскивается повторно.
- **Комментарии**: чисто текстовые — оптимистично с tempId, заменяется объектом из ответа; коммент с вложением — обычный спиннер до ответа (файлу нужен серверный id).
- **Поиск по доске** — клиентский фильтр по загруженным задачам (серверный `?search=` не используем).
- **Живых обновлений нет** (websocket/поллинг): осознанное ограничение v1 — правки второго участника видны после обновления страницы.

Существующее API, которое фронт использует как есть: auth (login/register/logout/me), boards CRUD + users, tasks CRUD, comments CRUD, вложения задач и комментариев (upload multipart `file`, list, download, delete), `GET /api/users/search?query=&limit=`.

## 6. Доработки бека

### 6.1 Новые эндпоинты

| Метод и путь | Что делает |
|---|---|
| `GET /api/boards/{boardId}/tasks/{taskId}` | Одна задача → `TaskResponse`. 404 — нет задачи в этой доске / не участник. Обязательно скоупить запрос по `boardId` (не повторять паттерн `CommentService`, см. 6.3). |
| `GET /api/boards/{boardId}/tasks/{taskId}/history` | История статусов → `List<StatusHistoryResponse>`, от новых к старым. |
| `POST /api/boards/{boardId}/statuses` | Создать колонку. Тело `StatusRequest { Name }` (`[MaxLength(100)]`). `Order` = max+1. |
| `PUT /api/boards/{boardId}/statuses/{statusId}` | Переименовать колонку. Тело `StatusRequest { Name }`. |
| `DELETE /api/boards/{boardId}/statuses/{statusId}` | Удалить **пустую** колонку (иначе 409 «в колонке есть задачи»); последнюю колонку доски нельзя (409). После удаления `Order` оставшихся переиндексируется в 0..n-1. |
| `PATCH /api/boards/{boardId}/statuses/{statusId}/position` | Тело `{ Position }` — переставить колонку. |
| `PATCH /api/boards/{boardId}/tasks/{taskId}/position` | Тело `{ StatusId, Position }` — перенос между колонками и/или перестановка. При смене статуса пишет строку истории. |

Семантика `Position` (оба эндпоинта): **0-based индекс в целевой колонке после изъятия перемещаемого элемента**; значения вне диапазона клампятся. Сервер переиндексирует затронутые колонки и возвращает 200 со списком всех затронутых сущностей `{Id, StatusId, Order}` (для статусов — `{Id, Order}`), фронт применяет его поверх оптимистичной раскладки.

Существующий `PATCH .../tasks/{taskId}/status` не удаляем (обратная совместимость), но дорабатываем: он проставляет `Order = max+1` в целевой колонке, чтобы не ломать сортировку. Фронт для DnD использует только `/position`.

`GET statuses` и `GET tasks` получают явную сортировку `ORDER BY (Order, Id)` (сейчас у statuses сортировки нет вообще).

### 6.2 Миграция

Одна миграция `AddOrdering`:
- `Status.Order int NOT NULL DEFAULT 0` — бекфилл по текущему `StatusId`;
- `Task.Order int NOT NULL DEFAULT 0` — бекфилл по `CreationDate` внутри своей колонки.

Уникальность `Order` не требуем; везде тай-брейк по `Id`.

### 6.3 Багфиксы и поведение

- **`TaskService.CreateTaskAsync` читает `WorkerId`** из запроса (сейчас исполнитель всегда = автор). Валидирует, что исполнитель — активный участник этой доски. Внимание на семантику id: `WorkerId` в API — это `User.UserId`, а `Task.AssigneeId` хранит `BoardUser.BoardUserId` — перевод обязателен во всех новых путях (create, `/position`, история).
- **Дефолтная колонка новой задачи** — `OrderBy(s => s.Order)` вместо `OrderBy(s => s.StatusId)` (после появления reorder «первая по id» ≠ «левая»).
- **Исполнитель опционален**: `TaskRequest.WorkerId → int?`, `TaskResponse.Worker → UserResponse?`. Чинится **вся цепочка, включая read-пути**: `GetAllBoardTasksAsync`, `CreateTaskAsync`, `UpdateTaskAsync` и новый `GET` сейчас проецируют `Assignee` не-nullable, а `AssigneeId` уже бывает NULL (удаление участника его обнуляет — `RemoveUserFromBoardAsync`) → готовый 500 на существующих данных. В `UpdateTaskAsync` lookup исполнителя становится условным (сейчас `WorkerId = null` дал бы 404 на каждый PUT).
- **Создание задачи пишет первую строку истории**: (начальный статус, автор = создатель, дата). Сущность хранит один статус на строку — «старый статус» не нужен.
- **Права:** редактировать задачу (`PUT`) может любой **активный участник** доски (= `BoardUser.IsDeleted == false`; сейчас может только автор). Удаление без изменений (автор задачи или владелец доски). 403 не используем: «не участник/нельзя» → 404, как во всём остальном коде.
- **Auth:** неверные логин/пароль → `401` «Неверный логин или пароль» (сейчас 409); 409 остаётся только у регистрации. `GET /api/auth/me` и `POST /api/auth/logout` получают `[Authorize]`. `/me` при валидной куке, но удалённом юзере возвращает 401, а не кидает исключение (сейчас 500). В `Program.cs` в довесок к существующему `OnRedirectToLogin` добавляем `OnRedirectToAccessDenied` → 403 для `/api/*` (на всякий случай, фронт его не ждёт).
- **Валидация:** `[ApiController]` на все 7 API-контроллеров; на request-DTO — `[Required]`/`[MaxLength]` зеркалом сущностей + `[MinLength(6)]` на пароль регистрации. Кривой ввод → 400 `ValidationProblemDetails` (см. §3), а не 500.
- **Скоупинг по доске:** `CommentService.GetAllCommentsOfTaskAsync` проверяет членство в переданном `boardId`, но не проверяет, что задача принадлежит этой доске — участник любой доски может читать чужие комментарии по перебору `taskId`. Чиним (задача обязана принадлежать `boardId`); новые эндпоинты пишутся сразу правильно.
- **`AttachmentResponse` перестаёт отдавать `FilePath`** (утечка серверного пути; фронту нужен только `/download`).
- **Заполнение `Author.Login` в списке досок**: `GetAllUserBoardsAsync`, `CreateBoardAsync`, `UpdateBoardAsync` сейчас проецируют `Author` без логина (`Login = null`) — сетка досок показала бы пустого автора. Заполняем как в `GetBoardAsync`.
- **Мелочь:** чиним битую строку заголовка Swagger в `Program.cs` (`"??? API v1"` → `"KanbanBoard API v1"`).

### 6.4 Итоговые формы изменённых DTO

```jsonc
// StatusResponse
{ "statusId": 1, "statusName": "To Do", "order": 0 }

// TaskResponse
{ "taskId": 42, "boardId": 5, "taskName": "…", "taskDescription": "…|null",
  "deadline": "2026-09-05T12:00:00Z", "dateOfMade": "…", "order": 3,
  "status": StatusResponse, "worker": UserResponse|null, "author": UserResponse,
  "commentsCount": 2, "attachmentsCount": 1 }   // attachmentsCount — только вложения задачи

// CommentResponse
{ "commentId": 7, "taskId": 42, "text": "…", "madeDate": "…", "isEdited": false,
  "author": UserResponse, "attachments": [AttachmentResponse] }

// StatusHistoryResponse
{ "statusChangeId": 3, "taskId": 42, "status": StatusResponse,
  "lastStatusChangeDate": "…", "author": UserResponse }   // author — через BoardUser→User

// AttachmentResponse (минус FilePath)
{ "attachmentId": 9, "fileName": "скрин.png", "dateOfUpload": "…", "uploader": UserResponse }
```

Стиль — как в существующем коде: паттерны сервисов (null → 404), `[Authorize]`, `CancellationToken`, плоские строки в телах ручных ошибок.

## 7. Обработка ошибок (фронт)

- `401` на любом запросе (кроме логина) → чистим стор → `#/login`.
- `404` доски → экран «Доска недоступна» (бек не различает «удалена» и «вас исключили»). `404` задачи при deep-link → тост + редирект на доску. `404` внутри модалки настроек → сообщение в модалке («Не найдено или недостаточно прав»), доску не роняем.
- `400` (валидация) → сообщения из `errors[поле]` под полями; `409` → предметное сообщение: «Логин уже занят», «В колонке есть задачи», «Нельзя удалить последнюю колонку».
- Сетевые ошибки / 5xx → тост «Что-то пошло не так», детали в консоль.
- Оптимистичные операции (DnD, текстовые комменты) при ошибке откатываются + тост.
- Пустые состояния: нет досок / пустая колонка / нет комментариев — тексты в `strings.js`.

## 8. Не входит в v1

- Живые обновления (websocket/поллинг).
- «Мои задачи» кросс-бордно (в сайдбаре зарезервировано место).
- Редактирование профиля, смена пароля, загрузка аватаров.
- «Покинуть доску» — на беке нет эндпоинта (владелец не может удалить себя, участник не может дёргать удаление) — не предлагаем в UI.
- Задача без дедлайна — `Deadline` на беке обязательный, форма создания требует дату.
- Мобильная вёрстка: цель — десктоп; на планшете терпимо, специально не вылизываем.

## 9. Проверка

- Каждый новый/изменённый бек-эндпоинт — прогон через Swagger: успех + 401/404/400/409. Внимание: cookie-auth — сначала `POST /api/auth/login` в том же Swagger (его `custom.js` уже шлёт куки).
- Самое хрупкое — переиндексация `/position` — дополнительно прогоняется скриптовым сценарием (curl): перестановки внутри колонки, перенос между колонками, границы (position за пределами), конкурентные переносы.
- Фронт — сквозные сценарии в браузере: регистрация → создание доски → колонки (создать/переименовать/перетащить/удалить) → задачи (с исполнителем и без) → DnD между/внутри колонок → комменты с вложениями → история → настройки → удаление → обе темы + system.
- Финальная приёмка: Павел открывает `http://localhost:5110` и смотрит глазами.

Автотестов не заводим (в проекте нет тестовой инфраструктуры, решение Павла) — риск осознан и компенсируется скриптовыми сценариями выше.

## 10. Порядок реализации (фазы)

1. **Бек, санитария**: `[ApiController]` + валидация DTO, auth-правки (401, `/me`, logout), права на PUT задачи, скоупинг комментариев, `Author.Login` в списках досок, `UseStaticFiles`, Swagger-заголовок.
2. **Бек, ordering и новые эндпоинты**: миграция `AddOrdering`, оба `/position`, CRUD статусов, `GET` задачи, `GET` истории + первая строка истории, багфикс `WorkerId`, nullable-исполнитель, DTO из §6.4.
3. **Фронт, каркас**: SPA-оболочка в Razor, `api.js`, роутер, темы/токены, логин, сетка досок, сайдбар.
4. **Фронт, доска**: колонки, карточки, DnD (между/внутри), поиск, шапка.
5. **Фронт, панель задачи и настройки**: панель с комментами/вложениями/историей, модалка настроек (участники/колонки/о доске), пустые состояния, тосты.

Приёмка после каждой фазы; фазы 1–2 проверяются Swagger'ом до начала фронта.
